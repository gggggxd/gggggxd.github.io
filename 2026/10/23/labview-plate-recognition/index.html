用 LabVIEW 做车牌识别：从手机摄像头到 OCR 的三个模块

  • | 图像处理

项目做完有一阵了，LabVIEW 也早就从这台机器上卸掉，程序跑不起来，但设计上的取舍还值得记一笔。这篇不复述说明书，只讲当时为什么这么做、哪里踩了坑、以及那组准确率数字背后的真实原因。

一、为什么绿色车牌是个麻烦

蓝色车牌是单一底色，取色相阈值一刀切下去，车牌子区域就出来了。新能源绿牌不是——它是从白到绿的渐变，同一个车牌上不同位置的白平衡、亮度都不一样。

这带来两个直接后果：

  1. 用单一 HSL 阈值去抠整块绿色区域，边缘会碎，框选不稳定；
  2. 渐变意味着”绿色”这个判据在车牌内部本身就是变化的。

当时查到的常规做法是上深度学习检测器，但 2020 版的 LabVIEW + NI Vision 生态里没有现成可用的推理链路，硬接 Python 节点又会把整个部署流程搞复杂。所以最后选了另一条路：不去对抗渐变，而是利用它。

二、整体结构

系统拆成三个模块，主 VI 负责串流程：

模块 实现 职责
图像采集 IMAQdx + IP Camera Adapter 手机 MJPEG 流 → LabVIEW 图像
车牌定位 subvi蓝色车牌提取.vi / subvi绿色车牌提取.vi 颜色空间分割 + 形态学 → 车牌 ROI
字符识别 IMAQ OCR + 训练字符集 ROI → 车牌字符串

主程序是一个 While 循环，里面用 Select 节点分「拍照模式」和「调试模式」两条支路：拍照模式从 IMAQdx 抓一帧写盘再读回来，调试模式直接读指定路径的图片。两条支路汇合后进 OCR，结果输出到前面板的 Read String 2。

先写盘再读回来这一步看着多余，其实是有意为之：调试时手边全是历史照片，走同一条”从文件读”的路径，才能保证两种模式的输入完全一致，出问题时不会混淆是采集变了还是算法变了。

三、图像采集：拿手机当网络摄像头

没有工业相机，用的是手机。

手机端装 IP 摄像头 App 起 MJPEG 服务，PC 端用 Configure IP Camera Adapter 把 http://<手机IP>:8081/ 注册成一个虚拟摄像头设备：

连上之后，MAX 里就能看到一个名为 MJPEG Camera "cam3" 的设备，IMAQdx 把它当普通相机用，后面 Open Camera → Configure Grab → Grab2 的流程完全不用改。

这个方案的好处很直接：零硬件成本、手机随手换、分辨率还不错。代价是延迟和稳定性都受 WiFi 影响，抓帧偶尔会拿到半张图——所以主循环里加了 等待(ms) 做节流，避免把网络缓冲抽干。

四、车牌定位：两条不同的路

这是整个项目里最值得说的部分。两种车牌最后走的是两套不同的算法，因为它们的可用特征不一样。

蓝牌：颜色阈值 + 形状匹配

关键在于最后的形状匹配。颜色分割能给出候选区域，但候选里可能有广告牌、蓝色车标、路面反光。用 IVA Shape Match 2 拿一个匹配分数，同时把长宽比、面积一起卡住，误检基本就压下去了。

蓝牌子 VI 的输出是四个坐标 x1Left / x2Right / y1Top / y2Bottom，也就是直接给一个矩形框。

绿牌：只用下半部分反推整个车牌

绿牌不能这么干。前面说过，白到绿的渐变会让整块阈值提取失败。

当时的观察是：渐变是从上白到下绿，所以车牌下缘一定是饱和度最高、最”绿”的那一段。于是思路反过来：

代码里能明显看到这条线索：绿牌子 VI 里有 数组大小、簇至数组转换、除、减、大于？ 一串纯算术节点，接在 Particle Analysis 输出之后——就是把测出来的矩形尺寸往固定比例上映射。

这个做法把一个”缺陷”（只有下半部分可靠）变成了”信息”（下半部分的位置直接给出了整个车牌的下边界），是整份代码里我最满意的一处。

绿牌子 VI 里还留着 IMAQ ColorMatch，用来在最后一步做颜色一致性校验，防止把别的绿色物块当成车牌。

两种方案的差异

蓝牌 绿牌
分割依据 整块 HSL 阈值 仅高饱和度下半段
定位手段 形状匹配 + 分数 尺寸比例反推
关键 subVI IVA Shape Match 2 IMAQ Particle Analysis
输出 矩形四点坐标 推算出的完整矩形

走哪种分支由前面板上的两个绿色 LED（蓝色车牌 / 绿色车牌）决定，本质是一个人工选择的开关。理想情况下应该自动判别，但实测场景里车型一眼可辨，做自动分类的收益不如把两条链路各自调稳。

temp_super_max.abc 是训练出来的自定义字符集文件，跟着 VI 一起走（用「当前 VI 路径 → 拆分路径 → 创建路径」在运行时拼出绝对路径，所以整个文件夹可以随便挪位置）。这一步很关键：默认字符集对国内车牌字体的识别率很差，把实际车牌样本喂进去重新训练之后才有可用的准确率。

失败处理上做了两级：识别不到车牌框时弹「请重新拍摄照片」，OCR 返回空串时弹「识别失败」——分开是因为这两种情况的排查方向完全不同。

六、测试与那组数字

测试地点选在宁波大学北区杨咏曼楼周围，下午 1:30–2:30 光照比较稳定，四个片区扫一遍，共 81 块车牌、580 个字符。

指标 全部 蓝牌 绿牌
车牌样本 81 68 13
字符样本 580 476 104
框选准确率 100% 100% 100%
完整识别率 72.84% 76.47% 53.85%
字符识别率 93.45% 93.28% 94.23%

单看字符准确率（93.45%）会觉得还行，但完整车牌识别率只有 72.84%，差了整整 20 个百分点。这个落差值得算一下。

蓝牌是 7 位字符。假设每个字符独立、识别率 93.28%，那么整块全对的概率是：

实际测出来 76.47%，明显高于理论值。原因大概是 OCR 对同一张车牌上的字符并不是独立判断的——同一块车牌的字体、光照、清晰度是共享的，一个字符能认对，旁边的通常也能，误差实际上正相关。这对系统是好事。

绿牌是 8 位字符（新能源车牌多一位）。同样算：

实际测出来只有 53.85%，低于理论值。

这就解释了绿牌完整识别率为什么难看：它的单字符准确率其实更高（94.23% > 93.28%），但字符多一位，误差累积更狠；再加上样本只有 13 块，一两块失手就能让比率大幅波动。样本量小是这份数据最实在的短板——它反映的是校园里新能源车的真实占比，但也意味着这个 53.85% 的置信区间相当宽。

七、踩过的坑

1. LabVIEW 的数据流不是顺序执行

最初把「抓帧 → 定位 → OCR」直接串在 While 循环里，结果 OCR 经常拿到上一帧的结果。LabVIEW 按数据依赖调度，两条没有连线的分支谁先跑是不确定的。最后用 Flat Sequence 强制了顺序，同时在关键节点之间用 error 簇串起来——这算是 LabVIEW 里最朴素的”加个大括号”。

2. 全局变量用多了会失控

Image Out 2/3/4 这类图像在多个子 VI 之间靠全局变量传递，写起来方便，但调试时完全看不出数据流。后来在关键位置插了 Overlay Rectangle，把中间结果直接画出来看，才定位到绿牌的分割阈值在高光区域会失效。

3. 调缩放比调算法更重要

前面板上有 X Resolution / Y Resolution，把输入帧缩到 1080×720。一开始以为这是为了省算力，实际调下来发现缩放本身就在做低通滤波，反而让形态学结果更稳定——原图的高频噪声会让连通域碎成一地。

八、如果重做

按现在的能力，有几步会换掉：

  1. 定位用检测器替代手调阈值。两条链路各自调参的成本很高，换环境就得重调。一个轻量检测模型（甚至模板匹配 + 更强的先验）能省掉大部分维护工作。
  2. 自动判别车牌类型，而不是让人点 LED。
  3. 把”完整识别率”设为主指标。单字符 93% 听着体面，但落到业务上是每四辆车就有一辆要人工复核——这才是真正决定系统能不能用的数字。
  4. 测试集要分层。81 块车牌里只有 13 块绿牌，且全在同一时段、同一片区域、同一光照。夜间、雨天、大角度倾斜一个都没覆盖，所以 72.84% 这个数字的适用范围其实很窄。

小结

这个项目的技术含量不在算法有多复杂，而在于在工具链的约束下把事情做成：没有检测模型，就用渐变的方向性做定位；没有工业相机，就把手机变成网络摄像头；OCR 通用模型不行，就自己训练字符集。

局限也很清楚——阈值和比例都是靠人工调出来的经验值，换个光照条件就要重新标定。这一点在测试数据的分层缺失上已经埋了伏笔。
