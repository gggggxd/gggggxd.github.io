从一段舞蹈视频到 G1 跳舞：GVHMR + GMR + SuperMimic 全链路实践

  2026-10-29 16:55 2026-10-29 16:55 Created   2026-11-11 17:58:56 2026-11-11 17:58:56 Updated

输入是一段 23.17 秒的舞蹈视频，固定机位、1280×720@30，舞者手里拿着篮球。输出是 Unitree G1 29-DoF 在 MuJoCo 里把其中两段舞跳完：动捕用 GVHMR，重定向用 GMR，策略训练用 SuperMimic，中间加了两层地面修正和一段过渡帧处理。

先看结果

原视频节选：dance_A（7.5–15.0 s）接 dance_B（15.0–22.0 s），共 14.5 秒。画面水印为原视频作者。

训练结果：蓝色实体是仿真中的策略，灰色半透明是参考动作；画面左上角是当前 clip、normalized return 和时间。

两段各约 9 秒的动作，按 Appendix F 的确定性协议回放，normalized return 0.8525，零失败；训练 3 小时，显卡是 RTX 5060 Ti 16 GB。

先把边界说清楚：只做到仿真，没有 ONNX 导出和真机部署；篮球没有建模，手臂动作按无球近似；原视频 22.8 秒处的单腿跳没有剪进任何片段。所以这不是“训练一个通用跳舞策略”，而是把一条从视频到机器人控制策略的链路完整跑通，并记录每一层的误差和返工。源视频是 B 站公开舞蹈视频（画面水印：小星Caze），这里只截取片段做链路验证。

一、整体链路

阶段 工具 输入 → 输出 关键结果
动捕 GVHMR 视频 → SMPL-X 世界坐标参数 7 秒片段推理 0.63 s，全身可见 100%
重定向 GMR SMPL-X → G1 根位姿 + 29 维关节角 0 帧穿地 >2 cm，0 帧关节超限
地面修正 自己写的两个脚本 人体/机器人分别做慢变垂直偏移 脚底高度中位数 1.60 / 1.09 cm
数据整形 pad_clip + csv_to_npz 30 Hz CSV → 50 Hz npz 472 / 447 帧，前后各 30 帧站立过渡
训练 SuperMimic-Reproduced 动作库 → 策略检查点 1024 envs，3 h，21000 迭代
评测 MuJoCo Warp 检查点 → Appendix F 指标 return 0.8525，失败 0/2

这条链路里，三个模型本身都是现成的，真正花时间的是接口：坐标系、单位、帧率、四元数顺序、脚底定义。下面按阶段拆。

二、单目动捕：GVHMR

原视频切两段：

片段 时间区间 帧数 内容
dance_A 7.5–15.0 s 225 帧 @30 运球、转身、脚步变化
dance_B 15.0–22.0 s 210 帧 @30 抬腿、绕球、较大幅度摆臂

GVHMR 做的是从单目视频恢复世界坐标下的人体运动。它把人体放在重力-视角坐标系里估计，输出的是 SMPL-X 的全局参数，而不是相机坐标系里的姿态。这里的机位是固定的，所以推理时加 -s 跳过视觉里程计：相机不动，就没必要让 VO 把背景的轻微抖动带进人体轨迹。

两段的 HMR4D 推理都只要 0.63 秒（7 秒片段）。真正占时间的是前面的预处理：YOLO 检测、ViTPose 关键点、ViT 特征。

动捕结果做了一轮量化质检：

指标 dance_A dance_B
全身可见帧 100% 100%
脚未出画 100% 100%
root 平移步长中位数 1.84 cm/帧 1.41 cm/帧
root 平移步长最大 5.66 cm 6.38 cm
水平方向总位移 0.583 m 0.289 m

轴角 global_orient 里出现了 6.27 rad 的帧间“跳变”。一开始以为是姿态翻转，后来确认是 2π 表示绕回：把轴角转成旋转矩阵，跳变就消失了。这类数值表示问题如果不看原始量，很容易误判成动捕失败。

叠加视频没有用 GVHMR 自带的 pytorch3d 渲染。原因很实际：官方 wheel 只到 torch 2.3，而这台 5060 Ti 是 sm_120，只能用 torch 2.8；pytorch3d 最后源码编译了 CPU 版，CPU 光栅化大约 22 秒一帧，不可用。于是改用 OpenCV 把 SMPL-X 顶点按相机内参投影回原视频，三角形按深度分 24 层、从远到近填充，再做半透明叠加。渲染不是链路必需环节，hmr4d_results.pt 在渲染前就已经保存，所以这个替代不影响后面的重定向。

另外，原视频里舞者在运球，手部经常被球遮挡。GVHMR 对手部的估计只能算“没有明显穿帮”，手臂动作按无球近似处理，这也是后面不建模篮球的原因之一。

三、重定向：GMR

GMR 用 IK 把人体关节对齐到机器人 link 上。对 G1，它输出 root_pos（3 维）、root_rot（4 维，xyzw）、dof_pos（29 维），转成 CSV 是 36 列、30 fps。

格式先逐项核对，再谈动作质量：

  • 关节顺序：左腿 6 → 右腿 6 → 腰 3 → 左臂 7 → 右臂 7，和 SuperMimic 的 G1_JOINT_NAMES 一致；
  • 四元数顺序是 xyzw，模长为 1；
  • 根位置单位是米，关节角是弧度。

直接跑 GMR，动作本身是对的，但机器人整体浮空：脚底离地中位数 7.6 cm（A）/ 14.8 cm（B），最高到 23 cm。原因有两层：

  1. 单目重建的垂直漂移。GVHMR 的人体网格最低点会从 0 慢慢漂到 +24 cm，但舞者其实一直踩在地上。固定机位、单目深度，这种尺度/平移漂移很典型。
  2. GMR 对齐的是踝关节。人的踝到脚底大约 8 cm，G1 只有约 3 cm。即使人体网格完全贴地，重定向后的机器人脚底仍然会浮 5 cm 左右。

所以不能简单给 root 加一个常数偏移。加常数只能修掉某一帧的浮空，修不掉随时间变化的漂移，还会把抬脚动作一起压掉。

四、地面锁定：这次链路里最实质的工程问题

处理分两层，思路一样：估计一个慢变的垂直偏移，从根位置里减掉；短时间的抬脚、腾空保留。

4.1 对人体：2 秒滚动最小值

对每一帧，取 SMPL-X 网格所有顶点的最低 z，作为“人体最低点”：

滚动最小值的前提是：任意 2 秒窗口里，至少有一只脚应该踩在地上。最低点因此可以代表地面，再平滑掉单帧噪声，就得到一条慢变偏移曲线。max(offset, 0) 是为了只往下修，不把动作整体抬高。

脚本在 scripts/ground_lock.py。它只改 smpl_params_global.transl 的 y，不改 smpl_params_incam.transl——相机坐标里的“竖直”不等于世界坐标的 up，改了反而会把动作拧掉。

4.2 对机器人：0.5 秒滚动最小值

人体贴地之后，机器人还会因为踝-脚底长度差浮 5 cm。于是对 G1 自己的脚底再做一次同样的处理：

  • 用 MuJoCo 加载 G1 的 MJCF，对每帧做前向运动学；
  • 取左右脚踝 roll link 上几何体（球体）的最低点；
  • 滚动最小值窗口缩到 0.5 秒，因为机器人每步都有支撑脚，窗口短才能跟上快速换脚；
  • 平滑后从 root_pos 的 z 里减掉。

脚本在 scripts/robot_ground_lock.py。这里用的是 G1 自己的几何，不是人的脚，所以踝-脚底长度差被真正消掉了。

4.3 修正后的指标

指标 dance_A dance_B
穿地 >2 cm 帧数 0 0
脚底高度中位数 1.60 cm 1.09 cm
最长悬空 0.43 s 0.70 s
关节超限帧数 0 0
root 速度中位数 0.48 m/s 0.36 m/s

B 的 0.70 秒悬空对应原视频里的抬腿动作，不是脚底修正失败；A 的 0.43 秒没有对应异常，仍在可接受范围。如果追求更严格的接触一致性，可以回 GMR 调 IK 的足部权重，或者用 SMPL 的 neutral 模型重跑，但这次判断它属于真实动作，没有继续压。

原始重定向结果全部保留，修正后的文件单独存 data/retarget/final/，随时可以回退对比。

五、过渡帧与 50 Hz 数据

重定向出来的动作从舞蹈中间开始、到舞蹈中间结束。策略训练和评测都希望机器人从站立姿态进入、再回到站立姿态，否则第一帧就是半蹲，reset 分布和评测起点会对不上。

scripts/pad_clip.py 在每段前后各加 30 帧站立姿态：

  • 关节角全零，根 xy 沿用片段首/尾的位置，yaw 取单位四元数；
  • 站立高度不手填，用前向运动学二分求解，使最低脚面正好落在 z=0；
  • 位置和关节角线性插值，根四元数用 slerp；
  • 30 Hz 下，dance_A 从 225 帧变 284 帧，dance_B 从 210 帧变 269 帧。

然后 csv_to_npz_batch.py 把 30 Hz CSV 转成 50 Hz npz：

片段 30 Hz 帧数 50 Hz 帧数 时长
dance_A 284 472 9.44 s
dance_B 269 447 8.94 s

这一步看起来只是格式转换，但它决定了训练时 reset 的初始状态分布。过渡帧不是“装饰”，是让训练分布和评测协议对齐的一部分。

六、训练：SuperMimic

训练侧用的是 SuperMimic-Reproduced，一个社区按论文从零复现的仓库，不是官方代码。它的核心不是 PPO，而是一个可微世界模型：先在想象 rollouts 上做 BPTT 更新 actor，critic 用 TD(λ)，动作库通过基于回报的重置采样来选片段。

这次没有改算法，只按仓库默认超参跑：

项 值
环境数 1024
batch size 1024
想象 horizon H = 32
UTD 0.4
训练时长 3.00 h
迭代数 21,000（约 2.0 it/s）
显存峰值 约 7 GB / 16 GB
动作库 2 clips / 919 帧 @50 Hz

训练末期的指标：

指标 值
world-model nse1 0.0051
world-model nse8 0.0073（论文 0.007–0.011）
train return 0.822
imagination return 2.713
survival 1.000

world-model 的 8 步开环误差已经进入论文区间，但 3 小时只是预算上限，不是收敛点：学习率的余弦衰减还没走完。按仓库经验，延长到 8–10 小时，或者加 --env.anchor-obs，还有继续压的空间。

七、评测：0.8525，零失败

评测按论文 Appendix F：每条 clip 从第一帧开始，确定性策略，不加噪声、不做域随机化；normalized return 定义为

1.0 是完美跟踪；训练里的 termination 一旦触发，这条 clip 就算失败。

片段 帧数 normalized return 是否失败
dance_A 472 0.897 否（472/472 步跑完）
dance_B 447 0.808 否（447/447 步跑完）
平均 — 0.8525 0 / 2

作为量级参考：仓库 README 里 LAFAN1 整段（100–300 s）单卡 3 小时约 0.56–0.59，BONES-SEED 短片段全量 7.1 小时 / 4×5090 是 0.93。我们这两段约 9 秒、带 30 帧过渡，0.85 落在两者之间；但评测集不同，不能直接横向比较，只能说明“这个量级是合理的”。

开头那段对比就是这两条 clip 的完整回放。除了回报，还统计了脚滑和 root 漂移：

指标 dance_A dance_B
脚滑（接触期平均） 0.307 m/s 0.169 m/s
root 漂移 平均 / 最大 / 最终 3.7 / 10.4 / 3.5 cm 6.8 / 14.8 / 8.7 cm
策略脚底最低点 -1.15 cm -1.27 cm
参考动作脚底最低点 -4.14 cm -0.75 cm

A 的跟踪明显更稳；B 的平均 root 漂移 6.8 cm，是 A 的近两倍，和 B 段抬腿、单脚支撑更多有关。这也解释了为什么 B 的回报低 0.09。后续如果继续做，B 是优先项：延长训练、调 GMR 的足部权重，或者加 anchor 观测。

八、踩过的环境坑

这部分不影响算法，但会直接决定能不能在一台 16 GB 消费级显卡上把链路跑起来。完整记录在 reports/REPORT.md，这里挑影响最大的几条：

问题 处理
GVHMR 官方 pin 的 torch 版本不支持 5060 Ti 的 sm_120 换 torch 2.8.0+cu128，三个环境互相隔离
pytorch3d 官方 wheel 只到 torch 2.3，pip 的 cuda_nvcc 又不含 nvcc 源码编译 CPU 版 0.7.9；渲染改用 OpenCV 投影
torch 2.8 默认 weights_only=True，挡住 ultralytics 权重 跑 GVHMR 时设 TORCH_FORCE_NO_WEIGHTS_ONLY_LOAD=1
chumpy 依赖 numpy<1.24（用了 numpy.bool） GVHMR 环境固定 numpy 1.23.5
uv 单连接下载，代理按连接限速 45 KB/s 导出 lock，12 路并行 pip download，172 个 wheel / 3.3 GB，离线安装
uv 留下 876 个僵尸锁，重试空转数小时 清锁后重新同步
SMPL-X 官方包不含 SMPL；v1.1.0 的 neutral 一度下载中断 先用 v1.0.0 的 male 顶替，后来确认 v1.1.0 完整（330,607,275 字节）并替换为真正的 neutral
下载器三个 bug：分块按字典序拼装、超时丢字节、漏 -L 修复后加 12 分块 md5 回归测试，已下的坏包重下

环境上最后是三个 venv：

阶段 Python 关键依赖
GVHMR 3.10 torch 2.8.0+cu128，pytorch3d 0.7.9（CPU），numpy 1.23.5
GMR 3.10 torch 2.8.0，mujoco，mink
SuperMimic 3.12 torch 2.14.1+cu130，mujoco 3.16，warp 1.18，mjlab@8bb2bc9

三个 venv 都放在 WSL 原生盘，不在 /mnt/f 上建：Windows 挂载盘的 IO 对 venv 的 import 和编译太慢。

九、局限与下一步

这次没有做的事，和做了但还不够好的事，分开列：

没做：

  • ONNX 导出、真机部署；
  • 篮球建模、抓取/运球；
  • 原视频 22.8 秒处的单腿跳没有剪进任何片段；
  • SMPL-X 性别特化模型，只用了 neutral。

不够好：

  • 两段各约 9 秒，纯本体感知策略在 100 秒级长片段会漂；仓库 README 已经指出，加 anchor 观测是已知解法；
  • B 段 root 漂移 6.8 cm，明显高于 A；B 的抬腿期还有 0.70 秒脚底 >2 cm，属于真实动作，但如果要更严格的接触一致性，应该回 GMR 调 IK 的足部权重；
  • 训练只跑了 3 小时，学习率没衰减完；延长到 8–10 小时是下一步最直接的提升；
  • 脚滑 0.169–0.307 m/s，策略脚底最低点 -1.2 cm 左右，还不是“零接触误差”。
